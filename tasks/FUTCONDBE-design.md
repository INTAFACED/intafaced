# FUTCONDBE design — futures conditional orders

One store, `trade.futures_conditional_orders`. Kinds are `stop_market`, `stop_limit`, `take_profit`, and `trailing_stop`. Money columns are `numeric`. The API speaks decimal strings through `parseAmount` / `formatAmount`. A kind that is missing a field it needs, or carrying a field it cannot use, refuses before any insert. `reduceOnly` defaults to true; `false` refuses, because an exit cannot open or enlarge. The side must be the closing side of an open position on that market (sell reduces a long, buy reduces a short). Anything else refuses `trade.conditional_would_increase`. `(user_id, client_order_id)` is unique. The same hash returns the first row. A different hash on that key is `trade.client_order_id_conflict`.

The trigger is `evaluateConditionalOrders`, and it runs only when `TRADE_FUTURES_CONDITIONAL_JOBS_ENABLED` is on. The flag ships off. A blank interval does not start a timer and does not invent a cadence. The price is the published mark. A missing mark skips the row. A trailing stop stores an extreme and moves it only in the favourable direction (a sell extreme only rises, a buy extreme only falls); the trigger is extreme ∓ distance. A cross claims the row with `UPDATE … WHERE status = 'armed' AND trigger_key IS NULL`, setting `trigger_key` to `fire:<id>` under a unique key, so a second worker updates zero rows and does not close. The winner then calls `PositionService.closeQuantity` with client close id `cond:<id>`. `stop_market`, `take_profit`, and `trailing_stop` use that close. `stop_limit` does not close at the mark: it hands the limit to the resting-limit path.

Failure is a status, not a log line. No open position after the claim cancels the row with `position_gone`. A close that throws marks the row `failed` and stores the typed code. The claim is not cleared, so it cannot fire again. Attached protection is two rows on the position (`attachment` `take_profit` or `stop_loss`) replaced in one transaction: validate both prices against the mark first, then cancel the previous armed pair and insert the new one. A wrong-side price throws before that write, so the previous pair stays. A long take-profit must be above the mark and its stop below; a short is the mirror. Equal to the mark is wrong-side. When `positions.status` becomes `closed`, a database trigger cancels still-armed attached rows with `position_closed`. The row that was already claimed is not armed, so the trigger does not cancel the exit that just fired.

Resting futures limits are refused with `trade.futures_resting_unsupported` and no order row. svc-matching lists opaque market ids from an operator open; it has no futures symbol. `PositionService` does not apply a matching fill (`entryFromOpeningFills` has no production caller, and a fill does not update `trade.positions`). A stop-limit that triggers calls that same refusal and the conditional row is `failed` with that code, which a get returns.
