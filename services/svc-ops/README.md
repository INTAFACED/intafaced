# svc-ops

Thin operator surfaces for CRM, team directory, warehouse revenue, projects, and custody tiers. **Not** a second money book, **not** payroll, **not** SaaS, **not** a key store.

Blank analytics replica refuses `ops.warehouse_unwired`. Empty warehouse is empty — never a fabricated `$0`. Team has no compensation field; `inventPayroll` refuses `ops.payroll_invent_forbidden`. Contacts are a local list plus named identity/support source lag.

GET `/ready` reports legacy warehouse/team `IDENTITY_URL` / `SUPPORT_URL` source configuration, never a live probe. Set is `ops.identity_unprobed` / `ops.support_unprobed`; blank is `ops.identity_unwired` / `ops.support_unwired`. Those legacy sources remain `hardcoded-absent`. Outreach uses separate live identity authority and notification ingress clients described below. Process liveness is not a custody claim.

Module id: `core-ops`. Edge prefix: `/api/ops`. Port: `4022`.

## Home's owner values

`home.config` (public, read only) answers Home's owner values for the customer app (HM-dashboard-03, HM-navigation-04, HM-widgets-03): `workListCap` (how many Needs you items Home shows, 1-50), `workListOrder` (work item kinds in the owner's order, each once), `searchResultCap` (how many help articles the header search lists, 1-20) and `noticeStripLimit` (how many of the latest announcements Home's strip shows, 1-10, HM-widgets-03), from `OPS_HOME_WORK_LIST_CAP`, `OPS_HOME_WORK_LIST_ORDER` (comma separated), `OPS_HOME_SEARCH_RESULT_CAP` and `OPS_HOME_NOTICE_STRIP_LIMIT`. Each is blank (`null`) until the owner sets it: Home then refuses its list with `home.work_list_cap_unset`, keeps the owners' order and says so, shows Help as not set, or has the announcement strip say its count is not set (`home.notice_strip_limit_unset`). ## Venue unit economics

`venueEconomics({period})` (`admin:read`: operator-only, so not `ops:read`, which ordinary sessions hold; the spec says `ops:read`, this is deliberately narrower) answers one month (`2026-10`): revenue from the same warehouse read as `revenue` (or its typed refusal, `ops.warehouse_unwired` and the lag codes, with the cost side still listed) and seven cost lines: liquidity, insurance_default_capital, custody, data, support, compliance, infrastructure. A line nobody entered is `not_entered`, never zero. With any line missing the report is `incomplete`, names the missing categories and marks the cost sums `partial`. Cost sums are per asset, exact on decimals. Fee revenue and net come from the ledger, not the warehouse points (they carry no asset or period): `feeRevenue` is svc-ledger's `feeRevenue` read for the UTC month, per asset (collected, returned, net of the two), or a typed unavailable (`ops.fee_revenue_unconfigured` with no `LEDGER_URL` or credential, `ops.fee_revenue_unavailable` for a refusal, timeout, malformed answer or an answer for another window). `net` is given per asset (fee revenue less the entered costs in that asset, exact on decimals, negative allowed) only when the ledger answered and all seven lines are entered; otherwise it is `unavailable` with `costs_incomplete` or `revenue_unavailable`. An unanswered ledger is never read as zero fees. The ledger lets svc-ops call two read doors and no other: this one and `reconciliationEvaluations` (below).

`recordVenueCost` (`admin:write`) enters one cost: period, category, decimal-string amount (not negative, no leading zeros, at most 20 whole digits and 18 decimals), asset, source note, and a two-person founder approval (`ops.venue_cost.record`, target `venue-cost:<period>:<category>`). A bad category, amount or period refuses (`ops.cost_category_invalid`, `ops.cost_amount_invalid`, `ops.cost_period_invalid`) before the approval is spent; no storage is `ops.cost_storage_unconfigured`. Entries are append-only rows in `ops.venue_cost_entries`; a new entry for the same period and category is the next version and supersedes the earlier one, which stays in the report history. Entry keys are `venue-cost:<period>:<category>:<version>`; the caller's idempotency key makes a retry return the stored row. No money moves and nothing here is a balance.

## Staff holds on funds

`staffHolds.list({userId})` (`admin:read`) shows one customer's staff holds with every ledger post made for each. `staffHolds.place` (`admin:treasury`) holds part of the customer's balance with a reason (at most 80 characters) and, optionally, an expiry in hours; available falls and total does not. `staffHolds.release` (`admin:treasury`) gives back part or all of what is held, and `staffHolds.confirm` (`admin:treasury`) moves exactly what is still held to the owner-named account. Release and confirm each spend a second founder's approval (`ops.hold.release` with the hold and amount, `ops.hold.confirm` with the hold; target `hold:<holdNo>`), so the requester alone is refused by identity. A replay with the same approval returns the stored answer and spends nothing.

The value never sits here: it is in the customer's own ledger pot `ops:hold:<holdNo>`, moved only by the `staffHoldPlace`, `staffHoldRelease` and `staffHoldConfirm` recipes under the keys `ops:hold:<holdNo>`, `ops:hold-release:<holdNo>:<releaseNo>` and `ops:hold-confirm:<holdNo>:<attempt>`. `hold_no` is one global sequence. Each post is first stored as a movement row with its number and key (`ops.staff_hold_movements`), under the hold's row lock, then sent once, then its answer recorded. While a movement is `settling` or `pending_retry` the hold takes no other action (`ops.hold_state_illegal`), so a release and a confirm asked for at once never both post. A release above what is held, or a confirm of anything else, is `ops.hold_amount_exceeds_remaining`; the ledger's non-negative hold balance is the backstop.

What an answer proves follows `classifyPostOutcome`: a named ledger refusal (for example `ledger.insufficient_funds`) marks the movement refused, and a refused place leaves the hold `refused` with nothing held. The posting freeze (`ledger.frozen`) and a request that never left the process keep the movement `pending_retry`, and a 5-second tick sends the stored request again under the stored key, waiting 5 s after the first send and twice as long after each further one, up to a minute (a client asking again waits the same). Any other failure, or a crash after a send, leaves the movement in doubt: it is never sent again, and the tick reads its key until the ledger's book decides (there, from module `ops` with the movement's reason: posted; there but another module's or reason's post: refused `ledger.idempotency_conflict`; still missing 7 minutes after the last send: `ledger.post_lost`). The tick works through the movements it looked at longest ago first, so a long queue never keeps the same ones at the front. Because the 7-minute bound is evidence, not proof, the tick reads a `ledger.post_lost` key again every 10 minutes for a day: a post found then is recorded as posted after all (a refused place brings its hold back with all it holds), or `ledger.idempotency_conflict` if another post holds the key; those are the only changes a settled movement can take (`20261024200000_staff_hold_rechecks`). A post committing more than a day after it was declared lost is not found: the ledger cannot yet close a key for good. The read by key is the ledger's `txByKey` door alone, which svc-ops may call; it says which module and reason booked a key, never the entries. The same tick releases what is left of each hold whose stored expiry has passed (cause `expiry`, no approver), checking the expiry against the clock again under the lock. An expiry release the ledger refuses is not tried again until another movement on the hold posts (for example a lost release found later): the hold stays held with the refusal on its movement, and a founder release is the way out. One hold's failure never stops the tick for the others.

Known limit, the same as every console-mode founder action here: if the process dies after identity spends a release or confirm approval and before the movement row commits, the retry is refused `action_approval.not_founders` (identity's replay of a spent approval carries no founder attestation). No value has moved; the founders issue a fresh approval.

Owner settings, both blank by default: `OPS_STAFF_HOLD_CONFIRM_ACCOUNT` names the `ops:hold-confirm:<slug>` account a confirm moves to (blank: confirm refuses `owner.decision` before any approval is spent, and nothing posts); `OPS_STAFF_HOLD_EXPIRY_MAX_HOURS` is the longest expiry a hold may be given (blank: an expiry refuses `ops.hold_expiry_unset`, and holds without one still work). Without storage every call refuses `ops.hold_storage_unconfigured`; without `LEDGER_URL` and a credential every action refuses `ops.hold_ledger_unconfigured`. svc-ops must hold svc-ledger grants for the three recipes before a keypair-mode ledger accepts its posts. No hold events are published yet.

## Protocol listing (pool hide, market delist)

`protocolListing.pools.hide|restore` and `protocolListing.markets.delist|restore` (`admin:write`) are the Protocol ops desk writes (D-order-controls-04). They live here because this service already consumes identity's four-eyes approval and the Protocol Plane holds no platform credential. Each needs a two-founder approval (`protocol.pool.hide`, `protocol.pool.restore`, `protocol.market.delist`, `protocol.market.restore`; target `<chainId>:<poolAddress>` lower-cased, or the upper-cased market symbol) and is idempotent on `<action>:<targetId>:<approvalId>`: a retry returns the stored result and consumes nothing. Every write input carries the `operationId` identity issued when the approval was proposed (consume refuses any other), and the approval is spent with a request id derived from the idempotency key. A crash between the spend and the write is not recoverable by a retry: identity's replay of a spent approval carries no founder attestation, so the retry is refused `action_approval.not_founders`, nothing is hidden, and the founders issue a fresh approval (fixing the replay is a svc-identity change). A second approval on a target already in that state is a `noop` with a note and is still logged. A hide is a LISTING decision, not an on-chain pause: nothing here pauses a contract or touches a balance.

Hiding needs a reason code from the list in force: the newest admin edit (`protocolListing.reasonCodes.set`, `admin:write`, logged with who made it), else `OPS_PROTOCOL_REASON_CODES` (comma separated), else the built-in default (scam_or_fraud, security_incident, contract_defect, legal_or_regulatory, sanctions_exposure, impersonation, abandoned_or_illiquid, owner_request). `reasonCodes.list` (`admin:read`) says which source is in force. A code outside the list refuses `protocol.ops_reason_code_unknown` before the approval is spent. `pools.list` and `markets.list` (`admin:read`) show every decided target with who approved it and under which policy version.

`protocolListing.hidden` is the public read svc-protocol and svc-dex use: pools by chain and address and markets by symbol, no reason and no signer, with `asOf`. Without `DATABASE_URL` and `OPS_DATABASE_POOL_MAX` every call refuses `ops.protocol_listing_storage_unconfigured`, so a reader never takes an unreadable list for an empty one. Decisions are append-only rows in `ops.protocol_listing_decisions`; the current state is `ops.protocol_listing_overrides`. The rollback `0011_protocol_listing.down.sql` refuses while any decision exists.

## Joint-restore stamps

`restore.record` writes each stamp to the append-only table `ops.restore_stamps` (one row per idempotency key; update and delete are refused by trigger), so a stamp survives a restart and a retry with the same key and body returns the stored row. A different body under the same key is `ops.idempotency_conflict`. Without `DATABASE_URL` and `OPS_DATABASE_POOL_MAX`, stamping refuses `ops.restore_storage_unconfigured` before any approval is consumed, and `restore.watermarks` returns `watermarks: null` with `storage.configured: false`. `restored` stays false on this read: nothing here restores a service. The watermark read does not probe the archive; `restore.backups` does.

If the process dies after identity consumes the approval and before the row is written, the retry cannot consume it again; the founders issue a new approval. No money is involved.

## Alert rules

`alertRules.list` / `get` / `versions` need `admin:read`. `create`, `update`, `setPaused` and `retire` need `admin:write` on a session with a second factor; `restore` of a retired rule needs `admin:treasury` as well, otherwise `ops.alert_forbidden`. Each takes a business `idempotencyKey` and a `reason`; edits also take `expectedVersion` (a stale one is `ops.alert_rule_version_stale`).

A rule watches one signal from the analytics metric catalogue (`ops.alert_signal_unknown` otherwise), one condition with a decimal-string threshold, an evaluation interval and a pending period. A blank threshold is `ops.alert_threshold_unset`; a blank interval or pending period is `ops.alert_interval_unset` (a pending period of 0 is a value the operator chooses). No number is invented. A check that returns no data or errors defaults to `alerting` (fail closed). Two live rules cannot carry the same non-empty label set (`ops.alert_labels_duplicate`); a rule with no labels is exempt.

Rules are rows in `ops.alert_rules`; every save appends a snapshot to `ops.alert_rule_versions` (update and delete refused by trigger), keyed by the idempotency key, so a retry returns the stored version and a retired rule is restored from its history, never destroyed. Without storage every call refuses `ops.alert_storage_unconfigured`.

**Evaluation.** A 5-second tick in `src/index.ts` runs `AlertEvaluator`: for each live, unpaused rule it reads the signal (`warehouseSignalReader` over `ops.revenue()`; a missing warehouse is an `error` reading carrying the typed code, an empty one is `no_data`) and, under a per-rule advisory lock, runs the pure `step` once the rule's interval has passed. When that cycle finishes, it records the pipeline heartbeat described below. A thrown cycle does not. States are `normal`, `pending` (condition holds, waiting out the pending period) and `firing`; health is `ok`, `error` or `no_data`. Comparison is exact on the decimal digits, never on JS numbers. A metric with more than one point (one per dimension) is `ops.alert_signal_ambiguous` and fails closed, because a rule cannot name a dimension yet and a sum would mix units. A rule has one instance, so editing its labels never starts a second alert; pausing or retiring a rule closes its open alert (a resolved event if it was firing) and resuming starts a new episode. `alertRules.states` lists rules with their stored state (a rule never evaluated has `status: null`); `alertRules.history` lists state changes newest first, needs an explicit `limit`, says when the page was cut (`truncated`, `cap`) and reports `retention: {configured: false, code: ops.alert_history_retention_unset}` because no retention period is set and nothing is pruned.

**Events.** State (`ops.alert_instances`), its history (`ops.alert_state_history`, append-only) and the announcing events commit in one transaction with an outbox row (`ops.alert_outbox`). Keys are business keys: `ops:alert_rule:<rule>:<version>` and `ops:alert:<opened|resolved>:<rule>:<instance>:<epoch>`; the epoch counts episodes, so a re-open after a resolve is a new event. `AlertOutboxPublisher` sends rows in order to an injected bus and stops at the first failure. The bus is not wired in this service yet (`/ready` reports `alerts.events: outbox_only`), so rows wait in the outbox, and nothing is announced that was not stored.

**Active overview (OPS-alerts-03).** `alerts.activity` (`admin:read`, explicit `limit`) lists stored pending and firing instances, firing first. No state store refuses `ops.alert_storage_unconfigured` and returns no list. A rule that was never evaluated is absent, not normal. `lastValue` stays null when the check had no value. Each row carries the rule name when the rule row is still there, and the panel link only when both `dashboardUid` and `panelId` annotations are set; a half pair is `ops.panel_link_incomplete` and is not stored.

**Reconciliation alerts (OPS-reconciliation-03).** A 5-second tick in `src/index.ts` reads svc-ledger's `reconciliationEvaluations` door (settled evaluations, oldest first on a microsecond `(finishedAt, id)` cursor, pages of 200) and `ReconciliationAlertStore.ingest`s each one in its own transaction. A run id already taken (`ops.reconciliation_ingested_runs`) changes nothing, so a re-read is idempotent. Each tick starts two minutes (`FEED_OVERLAP_MS`) behind its cursor, because the ledger's settle window is a clock bound, not commit order: a run whose commit landed behind a cursor already passed is still taken once, and the stored cursor only moves forward. A run svc-ops cannot store holds the cursor and shows as the source failing. Each failing asset (the ledger's own rule: a set, non-zero difference outside a set tolerance, on scaled integers) raises or counts on one live alert per fingerprint (control, asset, period start); a FAIL with no failing asset raises one alert with no asset. A repeat bumps `occurrences` and `lastSeen` on that alert, never a second alert. Every evaluation also updates its period in `ops.reconciliation_periods`.

The in-console notice: the first failure is `sent`. A repeat is `repeat_unset` while `OPS_RECON_ALERT_REPEAT_SECONDS` is blank (never re-sends, and the alert says so with the code), `not_due` inside the interval, `snoozed` under a live snooze, otherwise `sent`. Every outcome is a timeline row.

`alerts.list` (newest first on `(lastSeen, id)`, explicit `limit`, cursor), `alerts.get` (alert, timeline, snoozes) and `alerts.periods` need `admin:read`. Each answer carries the feed's `source`: `never_read`, `ok`, or `unavailable` with `ops.alert_source_unavailable`, the ledger's failure and the last good read, so a down ledger never looks like nothing failed. `alerts.acknowledge` (note required, `ops.alert_note_required`), `alerts.snooze` (an end after now, else `ops.alert_snooze_end_invalid`) and `alerts.unsnooze` need `admin:write` on a second-factor session and a business `idempotencyKey`; a retry returns the stored result, the key on another action is `ops.idempotency_conflict`. Acknowledge is a compare-and-set on `open`: of two founders at once one wins, the other gets `ops.alert_state_illegal` naming who acknowledged and when. Acknowledged is not green: a period is green only when its latest evaluation passed and it has no open and no acknowledged alert, so an ERROR or UNSET period is never green. The timeline is append-only, a snooze row only ever gains its expiry, and an alert's fingerprint and acknowledgement are never rewritten (triggers in `drizzle/20261029180000_reconciliation_alerts.sql`). Without storage every call refuses `ops.alert_storage_unconfigured`. Announcing these alerts as events is OPS-reconciliation-04.

**Heartbeat.** At the end of each completed evaluator cycle, `AlertEvaluator` appends one row to `ops.alert_heartbeats`. The actor is `system:alert-evaluator`, the reason is `evaluator cycle completed`, and the business key is `heartbeat:<cycle start>` (the clock reading when that tick began). A cycle that throws writes nothing, so a stopped evaluator cannot look healthy. `alerts.heartbeatStatus` reads those rows only. `OPS_ALERT_HEARTBEAT_MAX_AGE_SECONDS` blank leaves `overdue` null and names `ops.heartbeat_window_unset`. A window with no pipeline beat yet names `ops.alert_heartbeat_absent` and does not call that late. Overdue is a real comparison only when both the window and a pipeline beat exist. Raising an external alert when that beat is overdue is a later slice; this slice only records the beat and reports `overdue`. `alerts.heartbeat` (`admin:write`, second factor, reason, idempotency key) is a manual test beat. It appends to `ops.alert_test_beats`, not the pipeline table, so pressing it never resets the overdue clock. A retry of the same key and reason returns the row; a different reason is `ops.idempotency_conflict`. A blank actor is `ops.alert_actor_unset` and nothing is written.

**Templates.** `alertTemplates.save|get|list|preview` store a name, a title, a body and the variables those strings reference. A variable is `{{label:<name>}}` or `{{query:<name>}}`, and the save lists each one as `{ name, source: 'label' | 'query' }`. There is no default template and nothing here sends. A blank title is `ops.alert_template_title_unset` and a blank body is `ops.alert_template_body_unset`, both before the write. Creating a template under a name that already exists refuses `ops.template_name_taken`. An update with a stale `expectedVersion` is `ops.alert_template_version_stale`. The current row and its append-only version (actor, reason, idempotency key) commit together. `alertTemplates.preview` (`admin:read`) renders the title and body against sample data labelled `TEST` (every declared variable is the literal `TEST`, and `sample` is `TEST`) or against custom label and query values. Each referenced variable with no usable value is left in place and named in `missing` (`label:owner`, `query:value`). Save is allowed with a missing variable only while the quality policy is detect-only (unset, empty, or every requirement `detect`). While any requirement is `enforce`, that save refuses `ops.alert_label_required` and writes nothing.

**Quality policy.** `alertQuality.get` is null with `ops.alert_quality_policy_unset` until a founder saves one. An explicit empty requirement list is stored and findings name `ops.alert_quality_nothing_required` (checked stays null: nothing was asked). Otherwise `alertQuality.findings` names live rules missing a required label or annotation; it does not score them and it does not read a missing rule as a zero. `detect` does not block a save. `enforce` refuses `ops.alert_label_required` inside the rule save, before the rule row is written. Annotation keys are summary, runbookUrl, dashboardUid and panelId. Delivery, silences and contact points stay OPS-alerts-02.

**Later slices, not in this one.** Notification groups. Delivery errors on the overview, with Retry. Template groups, with unique names across groups. Create-rule-from-panel. The external overdue alert named above.

**Event subjects.** Declared in `packages/events/src/catalog.ts` and written to the outbox, not yet published: `coreOpsAlertRuleUpdated` (a rule version was created, edited, paused, resumed, retired or restored), `coreOpsAlertOpened` and `coreOpsAlertResolved`. Consumers: none yet.

## Durable outreach CRM

`outreach.capture`, `outreach.resume` and `outreach.answer` are public **POST mutations**. The browser creates a canonical 256-bit continuation capability independently of its UUID request key. Keep the capability in protected client storage; never put it in a URL, telemetry, ordinary logs or an email lookup. This capability is the proof for continuation, including another device; email equality supplies no authority. PostgreSQL stores its SHA-256 hash. An expired or incorrect capability refuses before any replay is returned. Capture returns a submission receipt only after contacts, organisation relationships, opportunities, tasks, attributed activity, request dedupe and the acknowledgement outbox commit together.

New public captures create separate unverified CRM contacts even when email addresses match. They neither attach platform identities nor replace prior contacts or questionnaire answers. Selected audience answers are immutable; a retry must retain its request key and exact payload. New audience answers require the current submission revision. Investor indicative contributions remain decimal-string business records. Unknown source keys remain untrusted hints with unknown campaign and recipient linkage.

The protected `outreach.owners` response retains `ownerUserIds` and returns the explicit configured ordered `{userId,displayName}` pair for Nitro and Phantom. These labels never infer names from email or shortened identifiers.

Private `outreach.listOpportunities`, `getOpportunity`, `owners`, `assign`, `changeStage`, `updateNextAction`, `addNote` and `engagement` require `ops:read` or `ops:write` and a live founder authority check. Identity authenticates the original signed principal and verifies active identity, current unrevoked MFA session and enabled founder entitlement on every request, including retries. API keys, subaccounts, expired tokens and shared dashboard actors cannot authorize CRM access. Assignment, stage and next-action writes lock the opportunity and check its revision (`updateNextAction` replaces the pending next-action task without a stage change or reason and records a `next_action_changed` activity); all staff writes bind their dedupe result to the authenticated actor and canonical input. Notes are append-only and their sequence is allocated under the same lock. Lists use `(created_at,id)` keyset cursors and literal name/email search (also matching contacts merged into the row's contact, reported as `aliasMatches`), with one batched lookup returning exactly the unique contacts associated with the visible page. Private page `submissions` companions contain exactly the visible unique submission IDs, actual questionnaire `completedAt` and the original submitted `organisationName`; merging a contact never substitutes the canonical organisation or infers completion from stage.

### Deployment inputs

1. Set `DATABASE_URL` to the ops role and publish positive integer `OPS_DATABASE_POOL_MAX`. Startup runs the ops-only migration under a transaction/advisory lock. Missing or unavailable storage refuses `ops.crm.storage_unconfigured`; it never reports a captured enquiry.
2. Set `OPS_OUTREACH_CONFIG` to JSON with `founders` (exactly two distinct verified founder UUIDs, ordered Nitro then Phantom), `initialOwnerUserId` (one of them), `continuationTtlSeconds` (60–2592000), IANA `timeZone`, `businessWeekdays` (ISO 1–7), `reviewHour` and `reviewMinute`. No founder ID, UTC timezone or review deadline is invented. Initial review is at that clock on the next configured business day. A DST gap moves to the earliest valid following local clock on the same date; a fold selects the first occurrence. A completely missing civil date refuses instead of silently postponing review. Holidays are not modeled. Founder IDs are normalized to lowercase before duplicate and membership checks.
3. Set `IDENTITY_URL`, `INTERNAL_SERVICE_SECRET` and `EDGE_PRINCIPAL_SECRET` consistently with the authenticated identity service. Missing authority wiring refuses private access.
4. `pnpm --filter @intafaced/svc-ops db:migrate` applies the migration; append `down` to reverse it. Down drops CRM data. Export and restore a verified backup before invoking down on populated storage. The migration runner preserves its journal and serializes parallel deployments. A role with database CONNECT and ownership of a preprovisioned `ops` schema can migrate without database CREATE; creating an absent schema requires explicit provisioning authority.
5. Set an isolated `TEST_DATABASE_URL` ending in `_test` for the PostgreSQL suite. The harness creates a separate database for each suite and tests restart persistence, replay privacy, concurrency, answer preservation, keyset pages and up/down/up reversal.

The public abuse limit is 30 requests per source IP per minute, counted durably even when capability checks fail. The process uses the socket peer IP and stores only a hash. Fastify proxy trust remains disabled. Behind the edge, publish its exact trusted CIDRs in `OPS_TRUSTED_PROXY_CIDRS`: only those socket peers may supply the edge-overwritten `x-intafaced-client-ip` header. IPv4, IPv6 and mapped IPv6 are validated and canonicalized. Untrusted headers and X-Forwarded-For supply no authority; missing configuration retains the safe shared-edge budget. Malformed CIDRs refuse startup and malformed headers from trusted peers refuse the request with a code that contains no address. Identity authority fetches reject redirects so signed principal and service credentials cannot be forwarded to another host. Fastify logs IDs and outcomes without questionnaire bodies or capabilities. Notification dispatch requires explicit transport and gateway configuration; no bulk campaign or blind resend capability exists.

### Integration and data operation

The acknowledgement outbox commits at initial contact capture, before questionnaire completion, with stable `acknowledgement:<submissionId>` keys. Its fixed email confirms contact details received only. One acknowledgement is sufficient; answers do not enqueue a second one. Optional marketing permission remains separate.

Set `NOTIFY_URL` and dedicated `OPS_NOTIFY_SERVICE_SECRET` matching notify's `NOTIFY_OPS_SERVICE_SECRET` to activate the durable worker. Ingress configuration is not a gateway probe. Each row retains the original submission recipient and immutable dispatch payload; founder contact merges do not redirect existing messages. Workers claim rows with leases and bound exact-body ops-only POSTs to three seconds, including response-body stalls. Lost ingress receipts recover through the same key and notify's durable outcome; ingress attempt counts are not provider-send counts. Notify owns the single provider attempt and retains uncertain acceptance as `unresolved`. Such rows are never blindly resent. A verified receipt may show gateway `accepted`, which never establishes arrival or delivery.

Protected `outreach.queueMessage` accepts only an opportunity revision, kind, staff text and reason with actor-bound request identity. It derives original contact/submission/recipient and commits an attributed queue activity plus a revision increment. Investor call invitations require saved investor answers and reviewed stage. The queue receipt is local persistence; `outreach.listMessages` refreshes actual dispatch evidence with bounded keyset pagination. Fixed notification wrappers escape staff text. Manual `recordInteraction` remains distinct from sending mail.

Document analytics report `disabled/api_access_unavailable` for the current Free entitlement, never fabricated zero views. No document-provider API key is required. A verified entitled provider read/import and delivery adapter remain separate live-integration work. Explicit campaign/source mapping is implemented locally; it neither confirms document access nor identifies a recipient.

Questionnaire originals and attributed activities are retained with their submission until a controlled whole-cluster erasure completes. Notes are additive; no public delete, merge, contact lookup or export API exists. The approved inactivity period is six calendar months in UTC, with separate expiring active-discussion reviews described below. Automatic retention remains disabled until deployment explicitly enables that policy. Before production, the owner must configure the correction mailbox, private export destinations and restricted backup operations. This implementation does not assert that retention, email, document import, domains or backups have been deployed.

### Founder workflow API

All workflow routes authenticate current founder authority on every request, including cached exports. Read scopes cover `metrics`, `listCampaigns`, `listSourceMappings`, `listDuplicates`, `getContactProvenance`, `listTasks`, `listWorkflowAudit`, `documentProviderStatus` and `documentViews`. `exportSubmissions` is a read-authorized mutation because it records an audited, actor-bound export receipt. Write scopes cover `upsertCampaign`, `upsertSourceMapping`, `mergeContacts`, `createTask`, `transitionTask` and `recordInteraction`. Strict shared versioned schemas reject unknown fields; bounded lists use filter-bound keyset cursors. Exports return at most 200 original submissions per explicitly requested page, including current saved answers, immutable `initialContact`, first actual completion time and separate original/canonical contacts. No hidden bulk-export operation exists.

Campaigns and opaque source hints require an explicit founder mapping. Capture snapshots the mapping/campaign revisions at that time; later edits do not rewrite historical attribution. Original and canonical contact provenance expose the first/latest known mapped sources without transferring verification or identity. Metrics count persisted opportunities by audience, stage and source, canonical contacts, incomplete submissions, overdue tasks and explicitly manual call records. Source groups cap at 200 with a truncation flag. No contribution amounts are converted into numbers or aggregated as balances.

Email equality only identifies duplicate candidates. `mergeContacts` requires explicit confirmation, a reason and both contact revisions. It serializes canonical graph edits and moves at most 200 opportunity links, preserving original contacts, verification evidence, identities, organisations, captured selections and questionnaires. Existing aliases flatten to the chosen canonical target. Conflicting existing platform identities refuse the merge; a missing identity never acquires another contact's evidence. Contact merge and workflow histories are append-only.

Public `outreach.addInterests` accepts only a current continuation capability, request ID, submission ID, expected revision and unique audience additions. It never removes a selection or changes saved answers. New audiences atomically create their own opportunities and primary review tasks, using the current canonical contact after a merge. A completed draft becomes incomplete until every newly selected questionnaire is answered; its first actual completion stays preserved. Invalid or expired capabilities refuse before replay. Like answers, a recovered idempotent response may contain an older draft: clients must resume for the current revision.

Every open opportunity retains a primary next action. Auxiliary follow-up/invitation tasks have explicit revisions and due dates; completion/cancellation races refuse stale revisions. Completing a primary task requires a replacement while the opportunity remains open. Closing an opportunity cancels pending primary and auxiliary tasks with attributed audit. Investor call plans/invitations/bookings require a saved investor questionnaire and a reviewed investor stage (`qualified`, `diligence` or `terms`). Other audiences retain their own pipeline stages. Call and follow-up records require an evidence reference and actual occurrence time; bookings also require an explicit scheduled time. All such records are `manually_recorded`: they do not send invitations or claim confirmed email/calendar delivery. Original investor indicative labels remain unchanged by pipeline/task transitions.

`papermarkFreeAdapter` implements the prepared bounded provider seam without making network calls. Provider status remains `disabled/api_access_unavailable` and view reads return typed `unavailable`, never an empty analytics page. A later entitled adapter must handle failed network/response reads as unavailable and validate provider data before exposing it; it must not infer platform ownership from a viewer email.

### Controlled contact-cluster erasure

`privacyPreview` and `privacyStatus` require a current founder MFA session and `ops:read`; `privacyBegin` and `privacyAdvance` require the same live authority and `ops:write`. The router rechecks identity on every request, including retries. There is no email-based identity proof. The founder must independently verify the privacy request and select the canonical contact UUID; passing an alias refuses. Preview includes all canonical/alias contact and original submission IDs, revisions, counts and a digest of their current state. It contains no email, name, questionnaire or staff text. `privacyBegin` requires the exact digest, canonical revision and explicit whole-cluster confirmation. A changed answer, note, task, selection, merge or dispatch state requires a fresh preview.

Beginning commits a restartable intent and one stable notification-erasure UUID for every original submission. Transaction locks serialize it against captures, answers, merges, staff writes and worker claims. That selected cluster's continuation, staff mutations and new dispatch claims then refuse; fresh same-email captures remain independent unverified enquiries. A previously claimed worker must finish its bounded ingress or lose its lease before advancement can proceed. Notify must still confirm its own erasure and tombstone, including after lease expiry; a late ingress cannot bypass notify's erased-submission refusal.

Each `privacyAdvance` calls only the shared notification port's `eraseSubmission` for at most one original submission. Missing transport, unknown/lost receipts, incorrectly bound receipts and in-flight notify refuse completion with a typed pending status. Identical actor-bound request retries drive the same intent with the same remote UUID; they never reset its original selection. A new request UUID requires the current intent revision. There is no automatic cancellation or rollback after remote erasure begins. A founder can inspect `privacyStatus` and explicitly retry after repairing the dependency.

Once every exact notify receipt is present, one ops-owned transaction removes originals, capability hashes, questionnaires, linked organisations no longer referenced elsewhere, opportunities, notes, tasks, interactions, messages, aliases, merge facts and the affected cached request/export results. Cached results that include a selected UUID are invalidated as a whole; unaffected exports and unrelated clusters remain. Deleted request UUID tombstones refuse reuse. The narrow `ops.crm_apply_erasure` function permits deletion only for the selected, notification-confirmed intent. Ordinary activity/history updates and deletes remain forbidden; direct deletion of original contacts, submissions, opportunities, tasks and outbox rows also refuses outside that procedure. No trigger is globally disabled and no other service's tables are read or written.

Erasure evidence contains only opaque IDs, actual actor kind and nullable founder UUID, a fixed reason code, revisions, snapshot digest, times and bound notify-erasure counts/receipts. Keep this restricted operational metadata under an approved policy; it is pseudonymous, not anonymous. `privacyRetentionStatus` reports `disabled/published_policy_unconfigured` when approved-policy configuration is absent; a retention-based erasure request then refuses `ops.crm.retention_unconfigured`. Configured status reports the fixed period, UTC clock, active-review maximum, actual automation configuration and last scheduler invocation. `lastSweepAt` is not a completed sweep or a health claim. CRM erasure does not delete a linked platform account, retract provider-accepted email, remove previously downloaded private exports, or establish deletion from third-party mail systems. Independently copied notes outside the selected cluster cannot be inferred from email equality. Physical storage, WAL and older backup disposal require the deployment owner's approved controls.

### Approved inactive-enquiry lifecycle

Set the existing `OPS_OUTREACH_CONFIG` JSON member `retention` to `{"publishedPolicy":"six_calendar_months_v1","automationEnabled":true}` only when deploying the approved public policy and deletion dependencies. Missing member keeps automatic retention disabled. `automationEnabled:false` configures the policy for protected manual review/retention commands without running automation. No additional environment variable, implicit founder identity or configurable retention period exists.

The meaningful-contact clock is the maximum actual event time across every linked original: original capture, newly saved prospect questionnaire answers, genuinely added audience opportunities, and evidence-bearing manually recorded `call_invited`, `call_booked` or `follow_up` interactions. Capture/answer/add-interest events use server time; backdated manual interaction uses its actual `occurredAt`, and future interaction timestamps refuse. Exact retries and unchanged interests/answers do not renew the clock. Internal notes, stage/assignment/task changes, exports, resume/polls/page views, capability refresh, acknowledgement creation and gateway acceptance do not renew it. This service has no editable public contact-update route. Six months use UTC calendar arithmetic with month-end clamp; for example 31 August reaches 28/29 February at the same UTC clock, independently of the task-review timezone and DST.

Protected founder/MFA `privacyRetentionReviewStatus` returns the last persisted review; `privacyRetentionReview` records an attributed, evidence-bearing `active`/`inactive` decision with reason, request UUID and expected canonical/review revisions. Each active review expires exactly 30 days after server review time, never resets meaningful contact, and a retry retains its original expiry. An inactive decision ends exemption immediately. A current active exemption also requires the same canonical cluster revision and an open opportunity. Merge invalidates an earlier review; closing all opportunities ends exemption. Review history is historical evidence, not a standalone promise of a current exemption. A stage alone never supplies an exception.

The owned nonoverlapping timer starts only after normal service startup (including restore reconciliation), runs every 60 seconds, and takes at most five bounded steps per pass. Each scan reads at most 100 candidate IDs but inspects at most five complete canonical clusters, yielding before the next candidate once one second of monotonic elapsed time has passed. The current whole-cluster check finishes atomically; this is a yield budget, not a one-second SQL deadline. The durable UUID cursor advances only for inspected candidates, so later invocations continue without skipping overdue contacts. Selection rechecks clock, canonical cluster and active review under the same exclusive privacy guard that excludes business writers and notification claims. It commits an immutable `system` intent with `requestedBy:null` before contacting notify. Pending retries alternate with fresh selection, retain exact remote UUIDs, and never silently mark unknown/in-flight erasure complete. Notification dependencies must reconcile before originals and review evidence are removed atomically. Sweep cadence, volume and unavailable dependencies may delay completion after eligibility; invocation time does not establish completion. The existing 200-original cluster limit refuses oversized erasure rather than deleting a partial cluster.

Approved outreach backups have a separate maximum lifetime of 30 days. That disposal, encryption, replica/WAL policy and independently retained current erasure archive require actual hosting configuration; this service does not infer them from its review period or certify deployment. `OPS_OUTREACH_RESTORE_QUARANTINED=1` refuses service startup, so neither HTTP exposure nor either background worker can run before reconciliation. Do not clear quarantine until a current durable erasure archive has been applied and checked.

### Backup and quarantined restore operation

The isolated PostgreSQL restore test invokes real `pg_dump` and `pg_restore` into a fresh owned database. It verifies original decimal strings, aliases, tasks, activity/audit history, request receipts and outbox, then applies later erasures to the older restored data. This proves the code path locally; it does not provision or certify a live backup service.

1. Restrict the ops database/backup role and backup destination. Use an approved encrypted backup envelope and restricted key access, including WAL, replicas and retention/disposal. Keep credentials in a restricted `PGPASSFILE` or the deployment secret system; avoid command history, logs and plaintext exported prospect data. PostgreSQL custom-format dumps are **not encrypted**. Set restrictive file permissions before generating them and verify the decrypted restore in an isolated database.
2. Preserve the current erasure archive in the independently owned receiver described below and retain its latest acknowledged generation separately from prospect backups. Production/staging erasure requires that receiver's durable acknowledgement before destruction. A local `export <new-private-file>` is mode-0600 diagnostic/maintenance metadata, not an independent current-archive or freshness substitute. Archive size limits refuse rather than truncate.
3. Restore into a quarantined database with HTTP access and notification workers/gateway disabled. Service startup refuses while `OPS_OUTREACH_RESTORE_QUARANTINED=1`. Apply all migrations. For **prod/staging**, set `DATABASE_URL`, archive URL/bearer and explicit `OPS_ERASURE_ARCHIVE_MIN_GENERATION`, then run `node services/svc-ops/dist/outreach/restore-privacy.js apply-current`. The independently current authenticated archive must be available and pass binding/freshness checks; there is no local-file fallback. Only **dev/test fixtures** may use `apply <current-private-file>`; group/world-readable files refuse. Legacy version-1 founder files remain readable in that fixture path. System authority must not be rewritten as a legacy founder.
4. Reconcile original notify erasure UUIDs and local pending intents while still quarantined, then verify recovered originals/caches are erased and dispatch cannot resurrect them. Matching newer local progress is preserved; prepared metadata does not itself prove completed deletion. Only then admit traffic or enable mail. Startup reconfirms independent publication before reapplying locally completed tombstones. An older backup or failed independent import cannot prove post-backup deletions are respected.
5. Keep old backups quarantined or dispose of them under the approved policy, and retain independently protected erasure metadata needed for future restores. Reversing the retention migration refuses when system intents exist, preserving authority evidence; otherwise down migrations drop CRM data and privacy evidence; they are not a privacy workflow. Preserve verified backups **and current independent erasure archives** before reversal. No production deletion, restore or backup was executed by these tests.

### Independent PREPARED erasure archive

`node services/svc-ops/dist/outreach/archive-receiver.js` is a standalone maintenance process: no identity, NATS, ledger, or prospect DB. Provision an independent OPS-owned PostgreSQL database/schema; set `OPS_ERASURE_ARCHIVE_DATABASE_URL` only on this receiver. It applies `drizzle/archive/0000_archive_receiver.sql`, not the CRM migrations. Never restore this database from a prospect backup. Its credentials/keys, table access and host placement remain operator deployment responsibilities; no provider or paid plan is required by this code.

Both OPS and receiver use `OPS_ERASURE_ARCHIVE_URL=https://<private-TLS-ingress-origin>` and `OPS_ERASURE_ARCHIVE_SECRET` (at least 32 characters, distinct from fleet credentials). Receiver additionally requires `OPS_ERASURE_ARCHIVE_ENCRYPTION_KEY` (canonical unpadded base64url of exactly 32 random bytes, stored separately from backups/runtime bearer), `OPS_ERASURE_ARCHIVE_TLS_INGRESS=trusted_loopback`, and optionally `OPS_ERASURE_ARCHIVE_PORT` (default 4122). It binds **127.0.0.1 only**. Standalone startup or shutdown failure closes the owned listener/database and emits only `ops.crm.archive_startup_failed`, never raw configuration or SQL errors. The authenticated TLS ingress must forward to this listener; prevent direct external listener access and restrict ingress networking. The configuration flag is an explicit ingress contract, not proof that TLS exists. Never place tokens in URLs or logs. Encryption uses AES-256-GCM with intent/digest authentication; database rows cannot be overwritten or deleted through normal SQL. Preserve the separate key for recovery; key rotation needs an explicit maintenance procedure, not replacement of the environment value.

The installed OPS runtime always supplies the publisher, including when configuration is absent. Missing/HTTP-in-production/shared-key configuration refuses `ops.crm.storage_unconfigured`; transport/receipt/storage errors refuse `ops.crm.storage_unavailable`. Development/test constructors may explicitly omit this test port; production and staging entrypoints have no bypass. The local `0005_crm_erasure_publication` migration stores original archivev2 bytes and SHA256 under the privacy gate. They commit before HTTP publication. Only a matching independent receipt permits notify erasure or local wipe; the three-second HTTP timeout includes response-body completion. Unknown acceptance retries the identical body. Reconfirmation precedes every pending step and startup completed-tombstone reapplication. Historical completed intents lacking a prepared packet refuse startup CRM recovery: reconcile/import independently reviewed historical metadata before enabling service, rather than inventing prior publication proof.

A PREPARED packet is **not completed deletion evidence**. It contains one frozen selection, actual founder/system actor, original notify erase UUIDs, bound privacy-request fingerprints, and all cached CRM request UUIDs selected by the exact erasure SQL predicate (including original capture). It contains no contacts, questionnaire answers, email addresses, or free-text review reasons. Independent `/current` assembles all immutable packets under a receiver transaction, verifies encrypted-body digests and generation/count coherence, and echoes a fresh client nonce. Publication also checks that the prospective aggregate remains schema-valid and within the bounded 16 MiB retrieval response before acknowledging; exceeding capacity refuses the new packet without erasure. A local file is not a freshness fallback. The independent database and latest generation must not be rolled back; a nonce cannot detect an operator restoring the entire independent database to an older point. Retain the latest acknowledged generation independently as a recovery watermark.

For production restore, keep `OPS_OUTREACH_RESTORE_QUARANTINED=1` and notify dispatch/gateway disabled. Run `node services/svc-ops/dist/outreach/restore-privacy.js apply-current` with OPS `DATABASE_URL`, archive URL/bearer, `APP_ENV=prod` (or staging), and `OPS_ERASURE_ARCHIVE_MIN_GENERATION` set to the independently retained latest receipt generation. The current authenticated receiver read must succeed. The command imports original prepared bytes/tombstones and preserves newer matching local progress; pending records remain frozen. Reconcile every original notify erase UUID and local intent while still quarantined using owner maintenance orchestration; only then lift the HTTP/mail quarantine. Existing local-file `apply` is refused in prod/staging. This process does not implement backup rotation, guarantee notification-database restoration, or supply external mail delivery proof; those remain joint restore/deployment responsibilities.

### Deploy notes

Admin and svc-ops must ship together, and the change is forward-only (do not roll svc-ops back on its own).

- **Wire shape.** `crmMessageSchema` gained `staffText` (the sent text, founders only) and the activity kinds gained `next_action_changed`. Both admin and svc-ops parse these with strict schemas. An old admin rejects a new svc-ops response that carries the `staffText` key or a `next_action_changed` history row. A new admin accepts an old svc-ops `listMessages` (a missing `staffText` reads as `null`), but it would then show no sent text. Deploy svc-ops and admin in the same release and do not leave a version gap.
- **No rollback of svc-ops alone.** Once a founder has saved a next action, `next_action_changed` rows exist in `ops.crm_activities`. An older svc-ops does not know that kind, so `getOpportunity` for those enquiries fails to parse. If a rollback is unavoidable, roll back admin and svc-ops together and treat any enquiry with a `next_action_changed` row as unreadable until the forward version is back.
- **Old idempotency receipts.** A `queueMessage` receipt stored before this release has no `staffText`. The output schema now defaults it to `null`, so replaying such a request returns a valid receipt instead of failing output validation. Messages whose stored send payload has no text also read back as `null`.
- **Retry keys.** `updateNextAction` fingerprints its due time as a UTC instant, so a retry that writes the same moment in another offset replays instead of conflicting.

`restore.start`, `restore.step`, `restore.finalize`, `restore.run`, `restore.runs` and `restore.backups` are the joint restore (OPS-ledger-desk-05). A run has one operator-chosen cut-off; each step (`restore_clean`, `validate`, `preview`, `finalize`) is its own append-only row in `ops.restore_steps`, accepted only in that order (`ops.restore_step_out_of_order`). The gates compare each stamp with the live `restore.watermark.read` of svc-ledger, svc-identity, svc-bank and svc-pay (not with each other, their sequences are independent) and refuse `ops.restore_watermarks_disagree` when a stamp is missing, a service cannot be read, a position differs from its stamp, or a service wrote after the cut-off. `finalize` also needs a second founder's approval bound to the run and cut-off, and `restored` is true only once all four rows exist. `OPS_RESTORE_TARGET` is the owner's storage target and ships blank, so `start` and `finalize` refuse `ops.restore_target_unset`. A blank archive URL makes `restore.backups` empty with `ops.restore_archive_unconfigured`. A set URL is probed: the manifest's full and incremental rows are listed as returned, an empty manifest stays an empty list, and a failed or unreadable probe stays `ops.restore_archive_unprobed` with no invented row. The step rows record what the operator attested. `BANK_URL`, `PAY_URL` and `IDENTITY_URL` (also the founder authority and approval wiring) point at the read doors; the fleet compose sets all three, and a blank one reads as unavailable. The test stack takes `OPS_RESTORE_TARGET` and `OPS_RESTORE_ARCHIVE_URL` from the labelled TEST profile (`tooling/profiles/test-owner-values/ops.json`); production leaves both blank. Events go to `ops.restore_outbox` only, until a bus is wired.
