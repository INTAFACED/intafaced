## The one finding that should be read first

**`GET /uc/monitor/heapdump` on `0.0.0.0:6001` returns the entire process heap to anyone
holding a copy of this repository.**

- `ucenter-api` and `otc-api` set `management.context-path=/monitor` with
  `management.security.enabled=false`, and guard the actuator with
  `security.user.name` / `security.user.password` — **both committed literals**.
- Both services are published to `0.0.0.0` (`:6001`, `:6006`) — confirmed via `docker ps`.
- Verified live, on this host, against the running fleet:

| request                                                                   | result                                                     |
| ------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `GET :6001/uc/monitor/env` with no credentials                            | `401`                                                      |
| same, with the credential from `ucenter-api/…/dev/application.properties` | **`200`, 9 KB**                                            |
| `GET :6001/uc/monitor/heapdump` with that credential                      | **`200`, 29 MB**                                           |
| `GET :6001/uc/monitor/trace`                                              | **`200`, 700 KB** — recent HTTP requests including headers |
| `GET :6001/uc/monitor/dump`                                               | `200` — full thread dump                                   |
| `GET :6006/otc/monitor/env` with `otc-api`'s own committed credential     | **`200`**                                                  |

A heap dump contains everything the process holds: the database password, the Redis
password, session material, in-flight user records, and anything else in memory. The
credential that unlocks it was in a tracked file. Repository read access was therefore
equivalent to full compromise of those two services.

**This was not on the audit list I was given.** It surfaced from checking the properties
files line by line rather than only the six items named.

**Changed on this branch:** `security.user.password` now reads `${COINEX_ACTUATOR_PASSWORD}`
with no default, in both modules.
**Owner must still do:** treat the old value as disclosed; the services keep running with
the old packaged jars until they are rebuilt and redeployed (see _Deployment consequence_).

## 1 · Keystore re-encryption

Full procedure in the runbook. Two things belong here:

**I did not execute any part of it.** No keystore was decrypted, written or moved; no
wallet RPC service was started; `ETH_KEYSTORE_PASSWORD` was not set anywhere.

**There is nothing to migrate on this host, and that is a checked claim, not an
assumption.** No `01_wallet_rpc` service is running; `/data/eth/data/keystore` does not
exist in any container; the module has never been compiled here; and MongoDB has no
`wallet` database at all — so no `ETH_address_book`, no `EUSDT_address_book`. The migration
is a **pre-flight** here. It is a real rescue procedure only for a legacy or production
deployment elsewhere, which is why it is written out in full.

A related finding that explains the above: **`01_wallet_rpc` cannot be built as committed.**
Its `pom.xml` lists an `xrp` module, and `vendor/upstream-exchange/01_wallet_rpc/xrp` is not
tracked in git. The reactor cannot resolve it. Nothing in that tree has been compiled, which
is also why none of its committed credentials were ever live _here_.

## 2 · The committed credentials

The audit list I was given named six items. **All six exist. None of them was the worst
one.** Verifying rather than trusting the list is what surfaced the actuator finding, and it
is the reason the count below is ~40 rather than 6.

### Method for "live" vs "dead"

"Dead" is not a guess. It means one of:

- the value is **upstream scrubbing** — a keyboard mash and/or points at the placeholder
  host `111.111.111.111`, which is not a routable address;
- the **module has never been built or run** here (`01_wallet_rpc`, per §1);
- the value is **overridden at runtime** by a higher-precedence source.

"Live" means the value is packaged into a jar that is running, or authenticates against
something reachable. I extracted `BOOT-INF/classes/application.properties` from the running
`ucenter-api.jar` to confirm which profile is actually packaged — it is `dev`, so the
`dev/application.properties` values are the ones that ship.

>
> **What this section said:** _"The auth wall from #86 is real and enforced —
> `RpcSecurityConfig` registers `RpcAuthInterceptor` on `/**`, requires `X-Rpc-Auth-Token`,

>
> 1. **It was not enforced on `bch`, `bsv`, `btm`, `eos`, `ltc` or `xmr`.** Those six do not

>    saying an unset variable leaves the placeholder unresolved and stops the service. **An
>    unresolved `${...}` placeholder in a properties file is inert until something asks for
>    the value.** On the six with no `RpcSecurityConfig`, nothing had `@Value("${rpc.auth-token}")`,

## 4 · The secret-scan gate

`tooling/ci/secret-scan.mjs`, wired into `pnpm verify` via `dod-gate.mjs` alongside
`brand-scan` and `custody-scan`, plus `pnpm scan:secrets` to run it alone.

**The rule:** for any assignment whose _key_ looks like a credential, the _value_ must be an
env placeholder `${VAR}`, empty, or a self-declaring placeholder. It separately flags URLs
embedding `user:password@host`, which the key-name check alone misses — the MongoDB URIs
were exactly that shape.

**Calibration, stated honestly.** The first run produced **159** hits. A gate that noisy gets
switched off, so I did not widen the rule until it went quiet — I looked at the distribution
and removed three categories that were structurally wrong to scan:

1. **i18n message bundles** — `member.password.error` is a UI string whose value is prose.
   One false positive per string per language.
2. **Dependency lockfiles** — integrity hashes and registry URLs.
3. **The matched dev pair** — `svc_trade:svc_trade`, `intafaced:intafaced`. A password
   identical to the username beside it carries no information an attacker can use.

That left six, of which three were genuine bugs in the scan — most importantly it rejected
`${VAR:?message}`, which is _stronger_ than `${VAR}` because compose refuses to start
without it. Final state: **0 violations, 92 credential-shaped assignments checked across 122
tracked config files.**

**Proven to catch, not just to pass.** A probe file with a literal API key, a
`user:password@host` URL and a `${VAR:-weakdefault}` was flagged on all three; the same
file's `${VAR}` and matched-dev-pair lines passed. Probe removed.

The scan prints the key name and file location, **never the value** — a CI log is not a
place to reproduce the secret it is complaining about.

> ### Two gaps in this gate, found 2026-08-02
>
> The calibration above is sound, and the narrowness is still the right call. But it left
> two holes that let the ECT withdrawal secret through for as long as the gate has existed.
>
> **Gap 1 — the key names the asset, not the secret.** `SECRET_KEY` matches keys ending in
> `password`, `secret`, `token`, `*key`, `credential`. `coin.withdraw-wallet` ends in
> "wallet". It held a raw signing seed. The key-name heuristic is the load-bearing
> assumption of this entire scan, and this is its counter-example — a credential can be
> **Deferred on land 2026-08-04:** partner PR #448 already edits `secret-scan.mjs`, so this
> PR does not dual-edit it. The ECT properties file no longer holds a literal
> (`${ECT_WITHDRAW_WALLET_SECRET}` + boot refuse on the disclosed value), which is the
> code-path fix. Expanding `SECRET_KEY` + the keystore-filename allowance remains a follow-up
> once #448 lands or is path-clear.
> **Gap 2 — `.java` files are not scanned, by design.** The second ECT secret was a literal
> argument to `sendFrom` inside a `main()` method. The design note above says a secret in a
> source file is "a different (rarer) problem and a much noisier scan", and that judgement
> is still defensible — but it is now a known-exercised gap rather than a theoretical one,
> and this tree contains 878 Java files nobody has read. **Not closed here.** Widening to
> `.java` is a calibration exercise of its own and would have been scope creep on a fix for
> a different hole. Recorded so the next person does not rediscover it by accident.

### Deployment consequence — the part that bites

The running jars were built **before** these changes and are mounted from a different
worktree. **Nothing in the running fleet changes until it is rebuilt and redeployed.** On
that rebuild, every service whose properties now hold `${VAR}` will **refuse to start**
unless the variable is set. That is the intended behaviour and the entire point — but it
means the rebuild is a coordinated step, not a background one. Set the environment first.

## 6 · Incidental finding — the shared test database

Not part of A1.4, found while running `pnpm verify` on a fresh worktree, fixed because it
costs one line each and it wastes an hour every time someone hits it.

`TEST_DATABASE_URL_IDENTITY`, `_PAY`, `_TOKEN` and `_P2P` are read by tests but were **not
in `.env.example`**. Unset, they fall back to the **shared `intafaced` database** — the exact
hazard `.env.example` already warns about two lines above. The symptom is a test failure that
looks like a real regression: svc-identity's KYC test asks for the oldest 200 pending records
and asserts its own new record is among them, and the shared database holds 239 pending rows
left by other worktrees.

Verified both ways: **164/165 against the shared database, 165/165 against `intafaced_test`.**
The four variables are now documented with that explanation.
