# svc-p2p — promise audit 2026-08-08

Tip: `c2e98cad` (audit baseline) · landed against `ff6b50c2`

Method: read every written promise the service makes about itself — README sentences
containing must / never / always / cannot / exactly / only / refuses, load-bearing code
comments, database CHECK constraints and UNIQUE indexes, and the error catalogue — then
tried to falsify each one against a state the service can actually reach.

**Provenance tags.** `[me]` = I read the code on tip and confirmed it myself. `[me+ci]` =
confirmed by a failing test on CI. `[reported]` = surfaced by a read-only harvest agent
and not independently re-verified by me; treat as a lead, not a fact.

A note on the shape of this service before the list: the **value** paths are the
best-defended code in this repo. Five layers deep, attacked with raw SQL, race-tested.
Every finding below that cost real money was on a path nobody had classified as a money
path — the notification and reputation side, where a commit is followed by a side effect
that nothing re-drives.

## Broken, fixed here

### 1 · A completed trade could pay out and then tell nobody → #1069 (merged) `[me+ci]`

`settle()` stamped `settled_at` and then published. `settled_at` is what removes a trade
from `sweepSettlements()`'s work list (`resolved_at IS NOT NULL AND settled_at IS NULL`),
and `settle()` returns early on an already-stamped row — so anything failing after the
stamp was never retried.

One refused envelope — a bus outage, a broker restart, a crash between the two statements
— and `p2p.escrow.released` plus both parties' XP awards were gone permanently. The value
had moved and no work list held the trade any more.

Not a crash window. An ordinary transient publish error was enough.

Fix: announce before stamping. Post (idempotent by business key) → announce (idempotent by
business key) → stamp. Any failure now leaves `settled_at` NULL and the sweep converges.
The trade is a re-publish for a permanent loss, and every publish here already carries the
business key that makes a re-publish safe.

Proven red on CI before the fix: `expected +0 to be 1` — the sweep found nothing to retry.

### 2 · The timeout sweep could refund a seller after the buyer had paid → #1075 `[me+ci]`

`sweepDeadlines` selects `(id, status)` for up to 100 trades in one query, then acts on
them one at a time, several round trips apart. `applyTimeout` dispatches on that status
without re-reading it, and `unwind` re-reads the trade only to confirm escrow exists —
never to confirm the trade is still in the state the decision was made about.

A trade read as `escrowed` that becomes `fiat_sent` before its turn comes is **refunded to
the seller**. `escrowed → cancelled` and `fiat_sent → cancelled` are both legal edges, so
`assertTransition` cannot tell them apart. The buyer has sent real money through their
bank, gets nothing back, and no dispute is opened — so there is no moderator to appeal to
and the trade reads as an ordinary expiry.

`escalateDispute` in the same file already re-validates under the row lock. The two sweep
paths that actually move value were the two that did not.

Fix: `unwind` takes the status the caller decided on and refuses if the trade has moved;
`recordDecision` re-checks it again under the row lock. The lock-level check also repairs
`cancelTrade`, which states the same rule in prose ("the buyer has declared the fiat sent —
open a dispute rather than cancelling") and lost it to the same race.

Proven red on CI before the fix: `expected 'cancelled' to be 'fiat_sent'` — the trade
really was refunded.

## Broken, parked

Each of these is real. None is fixed here, and the reason is given rather than implied.

### P1 · Every publish in this service is after-commit with no outbox `[me, partially]`

#1069 fixed the settlement window specifically. The same shape exists at seven other
commit-then-publish points: `p2pEscrowLocked` (after the escrow row commits),
`p2pTradeDisputed`, `p2pDisputeResolved`, `p2pOfferCreated`, and the three `p2pTradeExpired`
emissions. In each case a crash or a publish failure between the commit and the publish
loses the event with nothing to re-drive it.

**Why parked:** the general fix is a transactional outbox — a table written in the same
transaction as the decision and drained by a relay. That is a service-wide architectural
change, it touches `packages/events` (another session's lane this wave), and it deserves to
be designed once for every service rather than improvised inside svc-p2p. #1069 closed the
one window where the lost event was attached to money that had already moved; the rest lose
a notification, which is materially less severe.

**Not an agent call** in the sense that matters here: the design belongs in the events
package, and I do not own it this wave.

### P2 · `escrowIntegrity()` aggregates by seller against its own comment `[reported]`

The function reads per-trade escrow balances — correctly, since escrow is per-trade — then
sums them into a per-`(seller, asset)` bucket before comparing. Its own comment says
aggregating by seller "would hide cross-trade theft". Equal-and-opposite drift across two
of one seller's trades therefore reports `{ ok: true }`.

**Why parked:** I did not independently re-verify this one, and the fix (compare per trade,
report per trade) changes the shape of an operator-facing endpoint's response. It is a
genuine finding and worth a PR; it is not one I want to ship without reading the endpoint's
consumers first, and I ran out of lane before doing that. Flagged rather than guessed at.

### P3 · A timeout-opened dispute records a person who did not open it `[reported]`

When the `fiat_sent` clock elapses, the sweep opens a dispute and writes
`opened_by = buyerId`. Nobody opened it; the clock did. `opened_by` is serialised to the
wire and shown in the moderator queue, so a moderator sees a dispute attributed to a party
who never raised one. The same file's evidence handling argues the opposite principle
explicitly: "A guess recorded as a fact is how an audit trail starts lying."

**Why parked:** the honest fix needs a value for "the system opened this", and the
neighbouring column `moderator_id` is now constrained by `is_natural_person_id` precisely to
keep system principals out of attribution fields. Picking the representation for a
system-opened dispute is a schema decision that interacts with a migration another session
landed this wave (`0003_p2p_dispute_ruling_invariant`). Wrong moment to improvise.

### P4 · Retention floor does not actually bound the dispute SLA `[reported]`

`env.ts` claims "the floor below enforces that relationship rather than trusting it" for
payment-instrument retention versus the dispute SLA. It does not:
`P2P_INSTRUMENT_RETENTION_DAYS` has a minimum of 30, while `P2P_DISPUTE_SLA_SECONDS` has a
minimum of one hour and **no maximum**. A 60-day SLA with 30-day retention is an accepted
configuration, and the purge then races an open appeal — the exact thing the comment says is
impossible.

**Why parked:** a one-line cross-field refinement in the env schema would fix it, but it can
make a currently-booting deployment refuse to boot. That is an operational call with a blast
radius outside this repo, and it should be shipped deliberately rather than folded into an
audit wave.

### P5 · `fee_bps` is a bps value in a scale-0 numeric with no integrality check `[me]`

`takeOffer` accepts `feeBps?: number` with no integrality check and binds it straight into a
`numeric(8,0)` column. Postgres **rounds** rather than rejecting, so a fee of `12.5` becomes
`13` silently. The CHECK constraint bounds the range but not the scale, and `mulBps` — which
does demand an integer — never sees the fractional value because the column already rounded
it away.

**Why parked:** not reachable from the router (`trades.take` exposes no `feeBps`), and the
env var is coerced to an integer. It is reachable from any direct service call, including
the rank-fee-discount use the code comment anticipates. Real but latent; worth a guard when
that caller is written, and misleading to fix now as if it were live.

### P6 · The kill-switch cannot be flipped without a restart `[reported]`

`setTradingEnabled` has zero production callers. The switch is set once at construction, and
`/ready` reports the environment variable rather than the service's live flag — so the two
can diverge silently if anything ever does call the setter. It is documented as "§14 admin
controls" with no admin control behind it.

**Why parked:** this is the same repo-wide pattern the kill-switch reachability tooling
already tracks; fixing it in svc-p2p alone would make one service inconsistent with the
rest.

### P7 · The reputation-raises-limits loop is connected at neither end `[reported]`

`p2pLimitMultiplier` is declared in svc-identity's rank ladder, commented there as "svc-p2p
applies this", exposed by svc-p2p's `/internal/reputation/:userId`, and described in the
README as "the hot path other modules read". Nothing calls that endpoint and svc-p2p applies
no limit anywhere. The whole "a spotless P2P history raises limits platform-wide" sentence
the README opens with is written on both ends and joined in the middle by no code.

**Why parked:** the missing half lives in svc-identity, which is not my lane, and building
the connection is a feature rather than a fix.

## Documentation drift

Behaviour is correct; the sentence describing it is not. Recorded here rather than fixed,
because each one is a small PR and batching them into an audit wave would bury them.

- **"escrow is pooled per `(user, asset)`"** — false on tip, in the README and in two code
  headers. `tradeEscrowAccount()` returns purpose `trade:<id>`: one pot per trade, and
  `userEscrow` throws without a purpose. The guard those paragraphs justify is still right;
  its stated reason is stale by a ledger refactor. `[me]`
- **The README's constraint table omits three of the four guards** added by
  `0003_p2p_dispute_ruling_invariant`, and describes the moderator check as a `system:`
  denylist when tip implements a lowercase-UUID allowlist — i.e. the prose is stale in the
  _weaker_ direction than the code. `[reported]`
- **"236 tests"** — 360 `it(` declarations on tip. `[reported]`
- **`assertTransition` is "the only way a status column is ever written"** — `advanceToEscrowed`
  writes `status = 'escrowed'` guarded by a `WHERE status = 'created'` clause instead. Safe,
  but not what the sentence says. `[reported]`

## Could NOT break, having tried

The honest negative result. Each of these I attacked deliberately and failed to break, and
each is stronger than its documentation claims.

- **The escrow termination constraint.** I could not write a trade that is both released and
  refunded, from the service or behind it with raw SQL.
  `p2p_trades_resolution_matches_status_ck` makes the state unrepresentable, not merely
  unreachable. `[me]`
- **The terminal-deadline pair.** A terminal trade cannot carry a deadline and a live trade
  cannot lack one, so there is no row shape that is either invisible to the sweeper or
  re-resolvable by it. Both directions refused. `[me]`
- **The dispute-ruling trigger.** A disputed trade cannot reach a terminal state without a
  recorded, resolved ruling attributed to a natural person — enforced by a trigger, tested
  against eight id spellings and once with the constraint deliberately dropped to prove the
  test is not vacuous. This is the best-defended promise in the service. `[me]`
- **The moderator allowlist.** `is_natural_person_id` accepts only a lowercase canonical
  UUID. I could not get a `system:` principal, an uppercase UUID or a service account past
  it. The allowlist-over-denylist reasoning in the migration header is correct. `[me]`
- **One dispute per trade.** The unique index holds against concurrent opens. `[me]`
- **Evidence append-only.** The prefix-equality trigger refused every edit, reorder and
  truncate I tried from raw SQL. `[me]`
- **Double release, and eight concurrent releases.** Exactly one winner, value moves once,
  the book closes. The row lock plus the terminal guard genuinely compose. `[me]`
- **A refund against a never-locked trade.** Unreachable — and now doubly so, since escrow is
  per-trade, an empty pot would refuse on funds anyway. `[me]`
- **Lock ordering.** I looked for a deadlock between `takeOffer`, `eraseFor`,
  `resolveDispute`, `appendDisputeEvidence` and `escalateDispute` and did not find one:
  advisory owner locks are sorted, and every path takes trade-row then dispute-row in the
  same order. `[me, by reading]`
- **The fee split.** `buyerReceives + fee == amountLocked` exactly, with no second post and
  no zero-amount entry when the fee is zero. `[me]`
