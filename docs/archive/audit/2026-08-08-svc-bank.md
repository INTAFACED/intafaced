## Broken, parked — 1 · A re-used request id is answered with somebody else's position

**Class M. Patch written, tested, typechecked, and pushed to
`fix/bank-idempotency-conflict-parked` — no PR opened, because of the claim.**
Take it or drop it; it is one commit and it is rebased on tip.

### earn — no check at all

`services/svc-bank/src/earn/earn-service.ts`, `deposit()`. `positionId` is
client-supplied (`router.ts`: `positionId: z.string().uuid().optional()`). The
claim is `INSERT … ON CONFLICT (id) DO NOTHING` with nothing comparing the
existing row to the request.

Reachable state, second caller re-uses a live `positionId`:

1. the insert conflicts, so no row of theirs exists;
2. the ledger post moves **their** value into `earnStakeAccount(themId, asset, positionId)` — a fresh key, so it really moves;
3. `UPDATE … SET status = 'active' WHERE id = …` lands on the **first** caller's row;
4. `return this.position(positionId)` hands back the **first** caller's position, and the router answers "your deposit is open".

Blast radius, in plain words: their money is now sitting in a pot that no
`withdraw` of theirs can reach, because `withdraw` resolves the owner from the
row and refuses them. And the service's own reconciliation invariant — the
README's proof #1, that `principalOf()` from the table equals `stakedOf()` from
the ledger — is now false for both users at once. That is the `#1044` shape:
value in a place the books cannot see.

The same id re-used by the **same** user with a different amount is the everyday
version: "your 5 000 is earning" while 100 is staked and 4 900 sits in available.

**svc-token already does this correctly.** `claimStakePending` compares user,
amount and tier and throws `token.stake_conflict`. The svc-bank README says the
earn path is "same as svc-token's `stake`". It is not.

### loans — the amount is checked, the borrower is not

`services/svc-bank/src/loans/loan-service.ts`, `open()`. The guard added by
`bank.loan_principal_mismatch` is right and its comment argues the principle
correctly — then stops at `loan.principal !== input.principal`. Hold the
principal equal and a second caller re-using the id is answered out of somebody
else's loan:

- **active row** — told "your loan is open", with a status, an LTV and two ledger
  transaction ids, having locked no collateral of their own and drawn no
  principal of their own;
- **`pending` row** (the documented crash window, which `resumePending` and
  `abandonPending` exist because it happens) — `completePending` drives the
  **other** borrower's loan using **this** caller's collateral figure, out of the
  other borrower's account.

`productId` is unchecked for the same reason: the LTV above is computed against
the product named in this request, while the row carries the first call's asset
pair and APR.

### The patch on the branch

- earn: `reuseOrRefuse()` — compare user, pool and principal; `bank.position_conflict` on mismatch; return the existing position when the retry is genuine and finished, re-drive when it is genuine and still pending.
- loans: extend the existing guard with `loan.userId` and `loan.productId`; `bank.loan_borrower_mismatch`.
- router: both map to **409 CONFLICT** — the request is well formed and the same one under a fresh id succeeds; and neither message names whose the existing record is.
- 5 tests, 2 in `loans.test.ts` sitting beside the principal-mismatch tests that argue the same principle, 3 in `bank-service.test.ts`.
- `pnpm --filter @intafaced/svc-bank typecheck` clean; the money suites need Postgres and this machine has none, so they were never run green — **that is the one thing unverified about this patch.**

## Broken, parked — 2 · A standing order ignores a lock the same user set

`transfer-service.ts`. `resolveForDebit` / `resolveForCredit` exist, refuse an
archived space and a self-imposed `lockedUntil`, and have exactly **two call
sites** — both in the one-off `transfer()`. The scheduled path
(`fireOccurrenceInner`) calls `spaces.get()` for both ends and checks neither.

So: a user locks a savings space until December; the manual transfer out is
refused (`bank.space_locked`, tested); the standing order drains it every month.
Same for an archived space, where the README's "archiving moves no value" is
true of the archive gesture and false of the schedule that keeps firing through
it.

Reachability is trivial — `spaces.create` takes `lockedUntil`, and
`transfers.schedule` does not consult it either.

Coverage: one test, `refuses to debit a space the user has locked, and moves
nothing`, and it exercises the manual path only. This is failure shape #4 from
the wave brief — a guard no test executes on the path that matters.

Not fixed: same claim gate.

## Broken, parked — 3 · One stuck standing order stops everyone else's

`runDueTransfers` → `driveSchedule` → `fireOccurrence`, three nested loops with
no `try` between them. `settle()` deliberately rethrows anything that is not
insufficient funds — correct, because such an occurrence must not be consumed —
but the throw propagates out of the whole run.

The list is `ORDER BY next_run_at ASC`, and a schedule that threw never has its
`next_run_at` advanced. So it sorts **first on every subsequent pass, forever**:
one user's frozen asset, one unregistered-asset guard, one network fault to
svc-ledger, and no standing order on the platform fires again until an operator
notices. It is loud (the endpoint 500s) and completely blocking.

The fix is small and I did not write it: catch per schedule in `runDueTransfers`,
count the failure into `RunReport`, continue. It must stay a rethrow _inside_ the
schedule so the occurrence is not consumed.

## Broken, parked — 4 · One underfunded pool stops every other pool's interest

`accrueAll` loops `listPools()` and calls `accrue`, which throws
`bank.pool_underfunded` when the reserve cannot cover the day. Same shape as 3:
the throw escapes the loop, so every pool after the underfunded one goes unpaid
for the day. `listPools` orders deterministically, so it is the same pool
blocking first every time.

The README is explicit that an underfunded pool should be a **loud operator
problem** — it is right about that, and wrong that being loud is enough. One
operator's un-topped-up pool should not be able to withhold every other pool's
advertised yield.

## Could NOT break, having tried

- **Monthly occurrence arithmetic.** Attacked the classic drift bug (31 Jan → 28 Feb → stuck at the 28th). Computed from the anchor, so it returns to the 31st. `dueOccurrence`'s bounded search is correct at the clamped boundaries.
- **Double-fire under a retry, a second replica, or a DST rewind.** Two independent guards agree by construction: `unique(schedule_id, occurrence)` and the ledger key, both derived from the same pair.
- **Making up a March transfer in April.** The occurrence is consumed on rejection, with its code; there is no queue that could replay it.
- **Compounding interest by the back door.** Interest is credited to `available` and there is no `UPDATE … SET principal`; the schema test forbids an accruing column by name and by behaviour.
- **Rounding a unit into existence.** Every rounding in `interest.ts` is `floor`, in the reserve's favour, and the dust is counted rather than dropped.
- **Earning the native asset in a bank pool.** `assertEarnable` refuses at pool creation and at deposit.
