## Broken, fixed here

**1 + 2 · A settled yield window paid a staker who joined after it settled** → PR **#1076**

The recipient list was recomputed from `token.stakes WHERE status = 'active'` on
every call, so the resumability promise held only while the staker set stood
still — and it moves continuously.

Reachable state: window `w`, 100 IFC swept, one staker paid 100, rewards engine
back to zero. A second user stakes. The operator re-runs `w` — the operation the
method's own docstring calls safe. The already-paid user's `(window, user)`
reward key is spent so their post no-ops; the newcomer's key is fresh, so the
newcomer is paid a full share out of a window with nothing behind it.

Blast radius: `rewardsEngine` is a `house` account and §4.2 makes every
non-treasury account hard non-negative, so the payment comes out of some **other
window's undistributed revenue**, or the run dies mid-loop on insufficient funds
and leaves the window half paid. Either way stakers are paid from a pot that was
not theirs, and the operator is told nothing, because the run counted every post
it attempted — including the ones the ledger turned into no-ops.

Fix: freeze the plan (`0003_yield_window_plan.sql` → `token.yield_payouts`, PK
`(window_id, user_id)`), the same claim-before-post shape `token.stakes.status`
(0001) and `token.buyback_runs.status` (0002) already use, applied to the one
thing that was never claimed — _who_ the window pays. A re-run naming a different
revenue total is refused (`token.yield_window_mismatch`) rather than guessed at.
`alreadyPaid` on the result makes a re-run read as "already settled".

RED proof: commit `18fe694f` (tests only, recompute untouched) — CI **Tests
FAILURE**, four assertions, each reading as the bug:

```
FAIL  is resumable — re-running a window pays nobody twice
      expected '100' to be '0'
FAIL  does not pay a staker who joined AFTER the window was distributed
FAIL  finishes a window that crashed halfway, paying only whoever was missed
      expected +0 to be 1
FAIL  refuses a re-run that names a different revenue total for the same window
      promise resolved "{ windowId: 'w-changed', …(4) }" instead of rejecting
```

Doctrine gates, Gitleaks, Dependency audit and Prettier were green on the same
run, so the failure is the money behaviour and nothing else.

**15 + 16 · Retuning the emission curve could mint past max supply** → PR **#1083**

`token.supply_exhausted` is, in the README's own words, the only thing between a
mis-tuned curve and permanent supply inflation — and **no test named it**. The one
"schedule exhausted" case asserted `TokenError` and stopped there, and
`mintEpoch(10_000_000)` only ever reaches the first branch (`reward <= 0`). The
cap branch was executed by nothing.

It was also measuring the wrong thing. It compared what the CURVE says should
have been emitted by this epoch against `params.maxSupply` — and both live in
`token_params`, which §4.3 hands to governance and which the kill-switch argument
assumes can be retuned. So: mint epochs 0..k under a generous curve, then lower
`initialEpochReward`; `cumulativeEmission(k+1)` recomputes small, passes the cap,
and mints again on top of what is already circulating. Lowering `total_supply`
itself does the same from the other side. `emission_epochs_mined_within_scheduled_ck`
does not catch it — it bounds one ROW against its own schedule, never the total
against the cap.

Fix: measure the ceiling against the book — `SUM(mined_amount)` plus this epoch's
reward against `maxSupply` — inside the existing transaction and before the post,
with an advisory lock so two concurrent mints cannot each read a total that
excludes the other. The schedule guard stays; it still catches a mis-tuned curve
early and cheaply.

RED proof, commit `413873d0`: both new cases failed with
`promise resolved "{ epoch: 1, …(1) }" instead of rejecting` — i.e. on tip the
mint **succeeded**, past the cap, in both directions.

## Broken, parked

**3 · The README described an ordering bug that was fixed months of merges ago — taken in #1092, so this entry is closed.**

`services/svc-token/README.md` carries a block headed _"Known ordering gap, not
introduced by the honesty pass — flagged, not fixed"_, describing `recordBuyback`
posting the burn before the run row. That is no longer what the code does: #767
and migration `0002_buyback_window_claim.sql` moved the claim ahead of the burn
and replaced the unique index with an exclusion constraint. The README also still
lists `buyback_runs_window_idx (unique)` in its constraints table, and 0002
**drops** that index.

Kept out of #1076 because that PR's title was one story and this was another.
Landed separately as **#1092**, which also corrected the constraints table (it
listed `buyback_runs_window_idx`, which 0002 drops) and what
`emission_epochs_within_schedule_ck` actually catches — one row against its own
schedule, never the supply total. That last confusion is part of why nothing
tested the real ceiling until #1083.

**Residual, not a defect, restated so it is not lost:** nothing reads the
`houseFees` balance that `distributeRevenue`'s `sources` claims to sweep (audit
**T-03**). The figure is operator-typed. That is a declared §13 socket
(`token.yield`), the README says so plainly, and closing it needs the aggregation
job §4.3 specifies — not an agent's invention.

## Could NOT break, having tried

The honest negative result. Each of these I attacked and failed to falsify:

- **Stake id reuse.** Tried the exact attack that works on `svc-bank`'s earn
  deposit — a second user re-using a live `stakeId`. `claimStakePending` compares
  user, amount and tier against the existing row and throws
  `token.stake_conflict`. svc-token is the service that gets this right.
- **Double unstake, concurrent unstake.** The `unstaking → closed` update is
  conditional, so only one caller can win; the loser refuses rather than
  reporting a second success.
- **Unstaking a locked stake by re-driving.** The lock check is skipped on an
  `unstaking` row, which looked like a hole — but a row only reaches `unstaking`
  through the `active` branch, where the lock IS checked. There is no path that
  puts a locked stake into `unstaking`.
- **Yield paid to a `pending` stake.** `stakeOf` and the distribution query both
  filter `status = 'active'`; a claim that was never funded earns nothing.
- **A stake that unstakes between two runs of one window.** After #1076 their
  planned row survives and is still paid, which is correct — they were staked for
  the window that earned it. (Before #1076 they were silently dropped from the
  recomputed list and lost it. Fixing the first bug fixed this one too.)
- **Minting past the schedule.** `emission_epochs_within_schedule_ck` plus
  `cumulativeEmission` refuse; the kill-switch covers all three entry points.
- **Buyback window overlap.** The exclusion constraint refuses nested and partial
  overlaps, not just identical ones. Tried `[Jul 1, Aug 1)` against
  `[Jul 10, Jul 20)`; refused.
- **Params from source rather than the database.** `feeDiscountSchedule`,
  `buybackParams` and `emissionParams` all read `token_params` and refuse a
  missing row rather than falling back to the compiled defaults.
