## Q&A (required five)

### 1. Can stranger payment credit the wrong merchant/user?

**No — not via the public checkout or webhook path.**

| Control                                                                    | Evidence                                                                                                                                                              |
| -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Capability is the **link token** → one `payment_links` row → `merchant_id` | `readLink` by `token_hash`; open freezes `merchant_id` onto payment + session (`payment-service.ts:850–872`)                                                          |
| Payment insert always uses **link's** merchant, never a caller merchant id | `insertPayment({ merchantId: link.merchantId, … })` (`:850–858`, `:1936–1957`)                                                                                        |
| Capture credits **payment row's** `merchant_id` only                       | `recipes.paymentCapture({ merchantId: row.merchant_id, … })` (`:1212–1220`); recipe debits `merchantClearing(merchantId)` (`packages/ledger-client` `paymentCapture`) |
| Acceptance address is per **payment id**, not per merchant or per link     | `crypto-native.ts:157–165`; HD index from `paymentId` (`evm-chain.ts:135–152`)                                                                                        |
| Webhook matches `(rail_adapter, rail_ref)` only; no payment invented       | `applyWebhook` (`:1460–1475`); unique index `payments_rail_ref_idx` (`0000_pay_init.sql:105–106`)                                                                     |
| Unmatched verified event → refuse, no credit                               | `pay.webhook_unmatched` (`:1466–1475`)                                                                                                                                |
| Two payers on one link → two payments, two addresses                       | Test (`payment-service.test.ts:1320–1330`); session unique on `payment_id` (`0003:90–93`)                                                                             |
| Merchant-scoped APIs require owner                                         | `assertMerchantOwner` on create/authorize/capture/refund (`router.ts`)                                                                                                |

**Intended stranger behaviour:** anyone with the link token may pay **that** merchant. That is the product, not a bug.

**Not wrong-merchant:** overpay books what arrived on **that** payment (`authorize` may raise `payments.amount` to chain amount — `:1100–1108`); underpay fails without capture credit (`crypto-native.ts:224–237`). Dust / first-tx-wins can **stall** a correct pay (inherited M226-04), not redirect it to another merchant.

### 2. Does sandbox refuse on public checkout in staging/prod?

**Yes. `PAY_ALLOW_SANDBOX_RAILS` does not relax the public path.**

| Layer                                        | Behaviour                                                                                                                    | Evidence                                                                         |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Boot policy split                            | `policy` may be `allow-sandbox` with override; **`publicCheckoutPolicy` is `live-only` whenever `APP_ENV` ∈ {staging,prod}** | `posture.ts:160–183`                                                             |
| Mount                                        | `valueMovement: railPosture.policy` vs `publicCheckoutMovement: railPosture.publicCheckoutPolicy`                            | `index.ts:111–117`                                                               |
| Open gate                                    | `selectPublicCheckoutRail(…, this.publicCheckoutMovement)` **before** any row                                                | `payment-service.ts:796–803`                                                     |
| Adapter check                                | sandbox under `live-only` → `PublicCheckoutUnavailable` / `pay.checkout_rail_not_live`                                       | `posture.ts:270–273`, `301–330`                                                  |
| Rail not caller-chosen                       | only `PAY_CHECKOUT_RAILS` (default `crypto-native:crypto`); no `railAdapter` input                                           | `env.ts:124–155`; `router.ts:176–178`; zod strip test `router.test.ts:1019–1025` |
| Preference walks past sandbox                | refuses rather than fall back to sandbox under live-only                                                                     | `posture.test.ts:482–489`, `409–433`                                             |
| Writes nothing on refuse                     | no session, no payment                                                                                                       | test `payment-service.test.ts:1294–1305`                                         |
| HTML maps posture to 503, no rail disclosure | `stateForError` → `unavailable`                                                                                              | `checkout-page.ts:431–438`, `:176–189`                                           |
| `/ready` uses **same** public policy         | `publicCheckoutStatus()`                                                                                                     | `index.ts:188–208`                                                               |

**Dev/test:** public may use sandbox fixtures (`publicCheckoutPolicy: allow-sandbox`). Default `PAY_CHECKOUT_RAILS` still prefers `crypto-native` only; putting `card-sandbox` on that list in dev would allow public sandbox capture **by operator config**, not by stranger request.

**Merchant integration path (not public):** under `live-only`, sandbox **authorize/capture** still allowed (`assertRailMayMoveValue` skips non–value-leaving caps). That is M226-07 residual: platform-short if override + merchants use mock acquirer — **not** stranger-paid fabricated clearing on hosted checkout.

### 3. Claim-before-post / idempotency?

| Path                      | Ordering                                                                  | Keys / guards                                                                                                          |
| ------------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Session open              | Posture → tx (link lock, payment+session) → rail authorize **outside** tx | Session token SHA-256 unique; one session per payment                                                                  |
| Authorize                 | Lock payment; rail first; status machine; no ledger                       | Idempotent if already authorized/captured; `rail_ref` stable from payment id                                           |
| Capture (inbound)         | **Rail capture first, ledger second**                                     | Status gate; `payment.capture:<paymentId>`; re-run safe after crash mid-path (`:1135–1147`, `:1212–1228`)              |
| Webhook                   | Effect **before** dedupe marker (deliberate)                              | `rail_event_id` = `${adapter.id}:${event.eventId}` unique; concurrent race re-applies idempotent effect (`:1436–1557`) |
| Session complete          | Same tx as capture status update                                          | Only `open`/`expired` → `completed`; uses++ once (`:2004–2013`)                                                        |
| HTML open                 | 303 to session URL                                                        | Avoids re-POST double session (`checkout-page.ts:563–570`)                                                             |
| Refund / payout (related) | Ledger-first refund; runtime sandbox gate on value-leaving                | Outbound Class M still M226-01/02 — **not** inbound checkout booking                                                   |

**No public “I paid / complete” endpoint.** Only verified webhook (or authenticated merchant capture) advances money.

**Yes for checkout money.**

| Claim                                                       | Evidence                                                                                                 |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Capture posts only via ledger client + recipe               | `this.ledger.post(recipes.paymentCapture(…))` (`payment-service.ts:1212–1220`)                           |

| In-process maps on rails are custody observation, not books | Address book / observed (M226-06) — booking still recipe-only                                            |

### 5. Hosted checkout + live rail (#226) double-path bugs?

**No double-book / wrong-merchant fork between hosted and integration.** Both paths write the same `payments` shape (`insertPayment` shared — `:1927–1934`) and share `authorize` / `capture` / `handleWebhook`.

| Concern                                 | Verdict                                                                                                                                                                                                                                                 |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Hosted vs `payment.create` + named rail | Hosted: server rail only. Integration: caller may name `crypto-native` or (if registered) sandbox. **Different entry, same booking spine.**                                                                                                             |
| HTML form vs tRPC `checkout.open`       | Same `openCheckoutSession`; form has token/amount only, no rail (`checkout-page.ts:552–560`)                                                                                                                                                            |
| Session expire vs late pay              | Session can expire; payment stays; webhook still books correct merchant (test `:1354–1376`) — **single credit path**                                                                                                                                    |
| Webhook + manual capture                | Status + ledger key → second is no-op / duplicate                                                                                                                                                                                                       |
| Two sessions one payment                | Blocked by unique `checkout_sessions_payment_idx`                                                                                                                                                                                                       |
| Live watcher + authorize poll           | Both observe same chain address; capture still once                                                                                                                                                                                                     |
| Live outbound residuals                 | Refund/payout double-send (M226-01/02) is **after** successful capture; does not create a second inbound path                                                                                                                                           |
| Hosted “paid” UI vs book                | `completeCheckoutSession` in **same** capture transaction as ledger post (`:1230–1233`) — UI status cannot complete without book (for webhook/capture path). Watcher drop (M226-03) can delay auto-capture; does **not** mark completed without capture |

**Inherited live-rail risks that hit hosted payers hardest (not double-path bugs):**

- **M226-04** first-tx-wins dust on acceptance address → correct later payment ignored → stranger paid, merchant not credited until ops.
- **M226-03** watcher emit-before-2xx → auto “paid” poll stalls (manual/retry still possible if chain visible).
- **M226-01** multi-replica outbound — settlement/refund after capture, not open/session.

**Evidence:** Q1 table; unique `(rail_adapter, rail_ref)`; capture recipe keyed on payment id + row `merchant_id`; tests for amount freeze, dual-session addresses, late pay, webhook dup uses.

### P214-05 | P2 | `payment-service.ts` `completeCheckoutSession` / `readLink` maxUses · concurrency

**Claim:** `max_uses` is an **advisory** gate at open; two concurrent payers on `maxUses: 1` can both open, both pay, both be booked; `uses` may exceed max. Documented intentional (strand prevention), not a silent hard cap.

**Evidence:** `0003` comments + `completeCheckoutSession` always increments (`:1991–2002`); open checks remaining uses under link `FOR UPDATE` but cannot serialize two already-open payers paying after open.

**Risk:** Merchant expected single invoice payment may receive two; books correct, product surprise.

**Fix-owner:** product (hard single-use needs rail-level or stronger open+pay atomic design) / agent if product wants refuse-second-capture.

### P214-06 | P2 | `router.ts` `resolveLink` public output includes `merchantId`

**Claim:** Session view correctly omits merchant/payment/rail ids, but public `resolveLink` still returns `merchantId` (and link id). Not a credit bug; enumeration / correlation surface for token holders (token already capability).

**Evidence:** `router.ts:148–163` vs `checkoutSessionView` (`:65–74`); HTML does not render merchant uuid (`checkout-page` displayName only).

**Fix-owner:** agent — drop merchantId from public resolve if nothing legitimate needs it; keep on authenticated merchant APIs.

### P214-07 | P2 | Variable-amount links: stranger sets amount (and optionally asset)

**Claim:** On links without frozen amount/currency, payer-supplied values are frozen at open. No upper bound, no allow-list of assets at open (invalid asset fails later at authorize/rail).

**Evidence:** `openCheckoutSession` `:832–848`; form fields only when unfixed (`checkout-page.ts:236–250`).

**Risk:** Grief open sessions / absurd invoices; not wrong-merchant credit. Merchant who wanted fixed price must set amount on the link (fixed path ignores payer amount — tested).

**Fix-owner:** product (max amount, asset allow-list) if needed for abuse.

## VERDICT

**PASS-WITH-RESIDUALS** for hosted checkout (#214) money safety on tip.

Stranger pay cannot retarget merchant credit: amount/rail frozen server-side, payment and ledger capture bound to link merchant, addresses per payment id, webhooks match existing payments only. Staging/prod public path is **live-only** and ignores `PAY_ALLOW_SANDBOX_RAILS`; refuse is pre-write. Inbound booking is ledger-only with rail-first capture and business-key idempotency; hosted and merchant integration share one spine — **no double-path double-credit**.

What remains open is not a wrong-merchant hole: advisory `max_uses`, public `resolveLink` merchantId leakage, variable-amount abuse bounds, and **#226** live-rail residuals that hit hosted payers (dust first-tx-wins, watcher fire-and-forget). Outbound Class M (M226-01/02) is post-capture refund/payout risk, not checkout open.

**Ship posture:** single-process live crypto hosted checkout OK for pilot with eyes on dust griefing and watcher delivery; do not treat multi-replica outbound or mock-acquirer merchant capture as green.
