## Broken, fixed here

### F1 · Settlement freeze vs concurrent pre-settlement refund (money)

**Promise:** Settlement freezes payment set + gross, then posts those frozen numbers so the ledger key `settlement:<merchant>:<window>:<asset>` cannot return a different transaction than the DB records. Clearing is the pooled pot that backs the freeze.

**Falsification:**

1. `prepareSettlement` locked the **merchant** only, not the included payments, and did not exclude open `refund.posted` rows.
2. `refund` on a still-`captured` payment drew from **clearing** with no check for `settlement.included` on a **pending** settlement.
3. `merchantClearing` is pooled per merchant — settlement takes `gross` from the pool, not per-payment tagged funds.

Reachable bad path:

- Capture A ($100) and B ($100) → clearing 200.
- Freeze A+B, gross 200 (prepare commits).
- Concurrent refund A $100 from clearing → clearing 100.
- Capture C $100 → clearing 200 again.
- Settlement post takes 200 from clearing and marks A+B settled (A may stay `refunded` if status already flipped; B settles; **C's money funded the window** while C remains `captured` for a later settle that can no longer find its clearing).

Even without C: post hits insufficient clearing and the window sticks at `pending` forever, with `settlement.included` permanently excluding the payments from any future window (no release event).

**Fix:**

1. **`prepareSettlement`:** `SELECT … FOR UPDATE` each candidate payment (ordered by id) under the merchant lock; skip payments with open `refund.posted`; recompute nets after the lock.
2. **`refund` (status `captured` only):** refuse with `pay.settlement_in_flight` when a **pending** settlement has `settlement.included` for this payment. After the window posts, status is `settled` and refunds use available — unchanged and correct.
3. **`settleWindow` post:** re-lock included payments, recompute live captured−refunded sum; if ≠ frozen gross → `pay.settlement_desynced`, **no ledger post**.
4. Map both codes to **409 CONFLICT** (router + public-rest).
5. Tests (Postgres / CI): freeze+outage then refund refused; open `refund.posted` excluded from freeze; forced desync refuses post with clearing intact.
6. Withdrawal claim also compares `destination.kind` (was only `ref`) — same class of “resume must match the whole destination”.

**Not claimed fixed:**

- Operator cancel / release of a stuck `pending` settlement that still has `settlement.included` (no product cancel surface; desync leaves pending for ops).
- M226 residual crash-after-`eth_sendRawTransaction`-before-journal-`put` (README already names it; not rebuilt here).
- Auto-resume of refund phase-2 after `refund.posted` (deliberate refuse; operator reconcile).

## Broken, parked (not product-law inventing)

### R1 · Stuck `pending` settlement has no cancel / re-include path

Once `settlement.included` is appended, prepare forever excludes that payment. If post can never succeed (ops failure, adversarial SQL desync), clearing can sit until a human edits rows. Fix would be an explicit `settlement.released` (or cancel) event + operator procedure — product surface, not inventable on this audit.

### R2 · Broadcast journal window (M226-01 residual)

Crash after send, before `put`, can still double-send on retry. Postgres store closes multi-replica claim for the journalled case; the in-flight send window remains. Named in README; out of “local safe fix without custody redesign.”

### R3 · Refund phase-2 not auto-resumable

`pay.refund_in_flight` blocks all further refunds on the payment until a human reconciles. Protects double-send; costs operator work after a crash between ledger debit and rail. Documented intentional.

### R4 · First-tx-wins dust on acceptance address (M226-04)

Still true on EVM observation; stalls correct later pay; does not credit wrong merchant.

### R5 · PayFac permission areas not yet wired onto gateway money procedures

README honest: ownership is still `assertMerchantOwnership` equality. Tree exists; value areas not enforced on capture/refund yet. Direction residual.
